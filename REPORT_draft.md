# Отчёт: ассистент сервисной службы на Graph RAG

Репозиторий: <https://github.com/DanElis/llm-project-itmo>

Модель: Qwen3-4B-Instruct-2507, квантование Q4_K_M, файл GGUF из `unsloth/Qwen3-4B-Instruct-2507-GGUF`, в Ollama 0.40.16 зарегистрирован под тегом `qwen3:4b-instruct-2507-q4_K_M`, контекст 8192. Эмбеддинги: `bge-m3` F16 из `lm-kit/bge-m3-gguf`. Реестр Ollama с сервера прогонов недоступен, поэтому веса взяты с Hugging Face.

## 1. Задача

Диспетчер «ПолярТех» получает от клиента модель оборудования и код ошибки. Чтобы отправить инженера с нужной деталью, нужно пройти цепочку: код ошибки → отказавший узел → деталь этого узла в этой модели → не снята ли деталь с производства и чем заменена → остаток на складе → цена. Первые звенья разбросаны по разным документам (руководство, бюллетень), последние два есть только в ERP. Сейчас поиск занимает около 12 минут, и примерно в каждой двенадцатой заявке заказывают снятую с производства деталь, которую ERP потом отклоняет.

**Где ошибается плоский RAG.** Вопрос dev-06: «Какую деталь заказать при ошибке E-17 на AR-210?». В нашем прогоне плоский RAG ответил: «Деталь, которую нужно заказать, – пусковое реле», то есть назвал узел, но не номер детали. Чтобы ответить правильно, нужны три факта из разных документов: E-17 указывает на пусковое реле (руководство и регламент SP-104), реле в AR-210 – это P-1042 (раздел «Состав узлов» руководства), P-1042 снята с производства и заменена на P-1042B (бюллетень SB-2025-03). Поиск по сходству взял четыре чанка из руководств AR-210, AR-310, AR-220 и BZ-210, а бюллетень, где нет ни кода ошибки, ни модели, не попал в контекст, поэтому третье звено потерялось. В графе ответ лежит на пути `E-17 -INDICATES-> пусковое реле <-IS_A- P-1042 <-HAS_PART- AR-210` плюс `P-1042 -REPLACED_BY-> P-1042B`.

## 2. Решение

**Извлечение (FR-1, `extraction.py`).** Модели передаётся системный запрос со схемой: 7 типов сущностей с правилами записи имён и 8 типов связей с направлением «субъект → объект». Добавлен один пример диалога (вымышленные коды GS-999, P-9001, E-77, чтобы пример не путался с корпусом), в нём есть все 8 типов связей. Ответ запрашивается по `EXTRACTION_SCHEMA`. Потом идут проверки кодом:

- коды приводятся `normalize_code` и остаются, только если есть в `find_codes(текст чанка)`;
- названия приводятся `canonical_name` к словарю и дополнительно должны встречаться в тексте чанка (по основам слов, чтобы засчитывался и родительный падеж);
- связь остаётся, если оба конца прошли проверку и связь соответствует схеме;
- всё отброшенное считается в `dropped`;
- ответ, который не разбирается по схеме, запрашивается ещё раз, после второй неудачи возвращается пустой результат.

*Своё решение:* если модель перепутала тип у кода (например, `subject_type="Part"` для `AR-210`), тип берётся из вида кода (`code_type`), а связь не выбрасывается.

**Граф (FR-2, `graph_builder.py`).** `nx.DiGraph`, узел `Тип:имя` с `type`, `name`, `sources`. Ребро хранит `type`, `sources` (множество чанков) и `weight = len(sources)`, поэтому дубликат в одном чанке не увеличивает вес. Связи вне схемы отбрасываются. Встречные `REPLACED_BY` сравниваются по весу: остаётся более тяжёлая связь, при равенстве удаляются обе, число таких случаев пишется в `graph.graph["conflicts"]`.

**Сообщества (FR-3, `communities.py`).** Направления рёбер снимаются, веса встречных рёбер складываются, `louvain_communities(weight="weight", seed=42)`. Номера идут с 0 по убыванию размера. Для сводки код собирает дайджест: сущности, число отказов по узлам и моделям (суммы весов рёбер `FAILED`), цепочки замен. Модель только формулирует текст, сводка обрезается до 150 слов.

*Своё решение:* статистика одной линейки разъезжается по нескольким сообществам (например, «датчик температуры» Арктики попадает в другое сообщество). Поэтому если в сообщество входит узел `ProductLine`, в дайджест добавляется «обзор линейки», посчитанный кодом по всему графу: самый частый отказ, отказы по моделям, снятые с производства детали из руководств. Проверка на «идеальном» графе (извлечение правилами) показала, что после этого обзоры содержат ответы на все четыре global-вопроса dev-выборки.

**Режим local (FR-4).** Опорные сущности ищутся кодом: `find_codes` и `find_names` плюс поиск по основам слов («пускового реле» → «пусковое реле»). Если кода из вопроса нет в графе, сразу возвращается отказ без вызова модели. При двух и более опорах берутся рёбра всех простых путей длиной до 3 в неориентированном виде графа, при одной опоре – окрестность глубины 2 (сначала ближние рёбра, потом дальние, по важности типа). Затем добавляются цепочки `REPLACED_BY` от всех деталей и поставщик последней детали цепочки (нужно для вопросов вида «кто *сейчас* поставляет…»). Факты нумеруются, лимит 8000 символов. *Своё решение:* код дописывает подсказку «цепочки замен: P-2054 -> P-2054B -> P-2054C», потому что 4B-модели трудно собрать цепочку из разрозненных фактов. Источники – документы из `sources` использованных рёбер.

**Режим global (FR-5).** Шаг map: каждая сводка → JSON `{answer, score}` по `MAP_SCHEMA`, нечитаемый ответ пропускается. Шаг reduce: ответы со `score > 0`, отсортированные по оценке, объединяются одним вызовом. Если полезных ответов нет, возвращается отказ.

**Инструменты (FR-6, `tools.py`).** Пять схем function calling, склад задан `enum`. `validate_args` проверяет и нормализует аргументы до ERP: склад из списка, `part_id` – код типа Part, `qty` – целое > 0, `model` – код модели. `ErpNotFound` → `{"error": "данных нет…"}`, `ErpRejected` → `{"error": "ERP отклонила…"}`, `ErpUnavailable` пробрасывается агенту.

**Агент (FR-7 – FR-10, `agent.py`).** Цикл ReAct: модель получает `TOOL_SCHEMAS`, каждый вызов – `ToolStep`. Проверки кодом:

- неизвестный инструмент и `_raw`-аргументы возвращаются модели как ошибка;
- `part_id` должен встречаться в вопросе или результатах прошлых шагов, иначе подсказка «вызовите search_knowledge»;
- одинаковый вызов берётся из кеша;
- `ErpUnavailable` даёт 3 попытки, после них шаг с `error` и фраза «данные ERP получить не удалось»;
- лимит `max_steps`: итог без инструментов с пометкой «работа прервана».

Для заказа количество должно быть названо в вопросе (цифрой или словом), иначе агент задаёт уточняющий вопрос. Снятую с производства деталь агент не заказывает и подсказывает замену. При `confirm=False` агент возвращает `needs_confirmation` и `pending_action`.

Итоговый ответ сверяется с вопросом и результатами инструментов: все коды и все числа должны там встречаться. При расхождении модель один раз исправляет ответ, после второго расхождения агент отказывает.

## 4. Где граф помогает и где уступает

**Пример 1, граф выигрывает: dev-06** «Какую деталь заказать при ошибке E-17 на AR-210?»

- baseline: «Деталь, которую нужно заказать, – пусковое реле». Номера детали нет. Все четыре найденных чанка – из руководств: `manual_AR-210.md`, `manual_AR-310.md`, `manual_AR-220.md` и `manual_BZ-210.md`. Бюллетеня SB-2025-03 среди них нет: в нём нет ни E-17, ни AR-210, и по сходству с вопросом он проигрывает руководствам, где есть код ошибки. Судя по ответу, в контекст попали разделы с кодами ошибок и фраза «номера деталей зависят от модели», а раздел «Состав узлов» AR-210 с номером P-1042 – нет: руководство делится на несколько чанков. Даже если бы модель нашла P-1042, без бюллетеня она посоветовала бы деталь, снятую с производства.
- local: «При ошибке E-17 на AR-210 нужно заказать деталь P-1042B, так как P-1042 заменена на P-1042B». Ответ собран по пути `E-17 -INDICATES-> пусковое реле <-IS_A- P-1042 <-HAS_PART- AR-210` и цепочке `P-1042 -REPLACED_BY-> P-1042B`, в источниках есть `bulletin_SB-2025-03.md`. Агент на том же пути дополнительно получил из ERP остаток 3 шт. в Казани и цену 2630 руб.

Так же граф помогает на обзорном вопросе dev-13 «Какой узел чаще всего отказывает в линейке «Арктика»?»: baseline ответил «в базе знаний не найдено», а local и global ответили «пусковое реле». Число отказов посчитал код по весам рёбер `FAILED` (9 отчётов), и оно попало в сводку сообщества.

**Пример 2, граф уступает: режим global на точечных вопросах и цена.** На dev-01 «По какому регламенту устраняют ошибку E-17?» baseline и local ответили SP-104, а global – «в базе знаний не найдено». Сводка сообщества ограничена 150 словами и описывает отказы и замены, конкретные регламенты и поставщики в неё не попадают. Global верно ответил только на 2 из 5 local-вопросов и на 2 из 7 multihop. При этом он самый дорогой из режимов без инструментов: 9,6 вызова модели и 3374 токена на вопрос против 1 вызова и 1364 токенов у baseline. Индексация графа стоила 101 вызов модели (92 чанка + 9 сводок) и 210 тыс. токенов, плоскому RAG достаточно эмбеддингов.

## 6. Границы системы

На подтверждение человеку передаётся создание заказа (`create_service_order`). Агент не вызывает инструмент при `confirm=False`, а возвращает `needs_confirmation=True` и `pending_action`. Заказ не создаётся и при `confirm=True`, если количество не названо пользователем или деталь снята с производства. Ответ без данных – отказ «в базе знаний не найдено» с `refused=True`. Коды и числа в ответе агента проверяются кодом по результатам инструментов (FR-10).

Пример из прогона: на dev-21 «Оформи заказ: 2 штуки детали для устранения ошибки E-20 на BZ-120, склад Москва» граф дал неактуальную деталь (ошибка 1 в разделе 5). Ответ модели не прошёл сверку, агент вернул отказ и не подготовил заказ. На вопросе по умолчанию с E-17 и AR-210 агент выполнил `search_knowledge`, `check_stock` и `get_price` и ничего не заказывал: заказ создаётся только по прямой просьбе пользователя и после подтверждения.

## 7. Следующий шаг

Проверяемая идея: повторное извлечение для бюллетеней, в которых потеряна замена. Если в тексте чанка есть «снята с производства» и два номера детали, а в результате нет связи `REPLACED_BY`, код повторяет запрос к модели с короткой подсказкой: «в тексте есть замена детали, укажи связь REPLACED_BY от старой детали к новой». Ожидание: связь `P-2054B -REPLACED_BY-> P-2054C` появится в графе, Recall извлечения связей вырастет с 0.957, а dev-09 и dev-21 станут верными в режимах local и agent. Проверка: `make eval-extraction`, `make index`, `make eval MODE=local` и `make eval MODE=agent`, сравнить `relations.recall` и строки dev-09 и dev-21.
